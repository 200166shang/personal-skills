状态：历史初稿（2026-10-16），不作为当前执行规则。当前实现见[单课设计](../design.md)和[忠实模式修正](../fidelity.md)。以下保留当时文本，正文中的默认总结、拟定接口和开发状态均可能已被取代。

后续用户体验反馈要求保留完整原表达。当前默认已调整为忠实图文讲稿，取代本文早期“允许提炼归纳”的默认设定；摘要仅由用户明确要求时生成。详见[完整性修正记录](../fidelity.md)。

## 1. 已确定的目标

在 `personal-skills` 中增加两个小型、可组合的 Skill：

- `video-frames`：从视频生成带时间标签的预览图，按选定时刻提取单帧。
- `video-notes`：结合时间戳转写与预览图组织内容、选择配图，输出 Markdown 和静态 HTML。

笔记以好读为目标，允许归纳和合并重复内容，保留关键解释、步骤、例子、参数和限定条件。原始转写作为核对来源保留。模型负责理解、写作与选图；确定性工具负责处理文件、截图、校验和渲染。

下载与本地转写复用现有技能。Library 登记、Learning State、Questions、Topics 以及其他 learning 工作流均不参与。`media_operator` 作为一个调用入口，两个新 Skill 也能被其他具备相应工具能力的智能体独立使用。

## 2. 开发交付方式：独立工作树、新分支、PR

这是用户明确要求的实施约束：真正开始实现时，从更新后的 `origin/main` 创建独立 Git 工作树和 `codex/` 新分支，在新工作树中开发、验证、提交并创建 PR。当前工作分支不用于功能迭代。

实现使用独立工作树和 `codex/video-notes` 分支。方案编写阶段没有修改技能；后续实施按用户指示在新分支完成。

后续交付要求：

1. 先检查当前附属工作树、工作区改动和远程主线，再创建合适的工作树及新分支。
2. 功能源码、技能说明、必要测试、README 更新全部进入同一可审查 PR；初版两个技能保持配套，避免拆成不可运行的中间交付。
3. 小视频测试、案例样张和整集笔记放在仓库外；PR 中记录结果与验证方法，不提交课程媒体、缓存或包含本机路径的运行状态。
4. 在新工作树完成构建与案例验证后 push 新分支、创建 PR，并把 PR 附加到当前聊天。PR 创建不等于获准合并，不自动合并。
5. 本机 `media_operator` 配置在 PR 中提供可审查的接入说明或配置片段；实际本机修改单独报告，不能将仓库外的修改假装成 PR 已包含的内容。

## 4. 借鉴 BiliNote 的机制

源码研究版本：`90940fde4d224d0f69ad99674f4af0a1ea52d3c4`。此次复用的是下面的生成机制：

1. 带时间的转写提供讲解内容与时间定位。
2. 视频定时抽帧，生成带时间标签的预览拼图。
3. 模型同时查看文字和对应预览，组织笔记并提出配图位置与时刻。
4. 工具提取原视频单帧，将配图标记替换为真实图片。
5. 从同一份 Markdown 生成有统一样式的阅读页面。

依据：[教程风格及配图提示词](https://github.com/JefferyHcool/BiliNote/blob/90940fde4d224d0f69ad99674f4af0a1ea52d3c4/backend/app/gpt/prompt_builder.py)、[预览拼图](https://github.com/JefferyHcool/BiliNote/blob/90940fde4d224d0f69ad99674f4af0a1ea52d3c4/backend/app/utils/video_reader.py)、[截图替换](https://github.com/JefferyHcool/BiliNote/blob/90940fde4d224d0f69ad99674f4af0a1ea52d3c4/backend/app/services/note.py#L656-L676)、[Markdown 阅读器](https://github.com/JefferyHcool/BiliNote/blob/90940fde4d224d0f69ad99674f4af0a1ea52d3c4/BillNote_frontend/src/pages/HomePage/components/MarkdownViewer.tsx)。

我们的增量是：明确同一时间窗口的文字与图片关系、查看最终单帧后确认、任务独立目录、完整尾段处理、可恢复进度，以及可离线移动的 HTML 图文包。源码机制与最终效果相似度分别验证；采用相近提示词不保证任何模型都生成相同质量的笔记。

## 5. 两个 Skill 的职责和写法

### video-frames

独立能力：给定视频，浏览某段画面或提取指定时刻截图。描述中只写实际触发条件，例如“生成视频时间标记预览图，或提取指定时间的单帧”。

`SKILL.md` 保留：输入要求、预览/单帧两种操作、命令入口、时间基准、输出与失败条件。具体命令参数使用 `--help` 或一份 CLI 契约，避免在多处重复。

画面工具不做内容摘要、OCR、课程分类或自动选图。预览图给模型看，最终截图进入笔记。工具保留画面宽高比，标签放在单独区域；尾部不足一整组时保留已有帧，避免遗漏尾段。提供缩略预览时，不把放大低分辨率素材描述为恢复了清晰度。

### video-notes

独立能力：输入视频和时间戳转写，组织并输出图文笔记。它依赖 `video-frames` 提供画面处理，自己不维护第二份抽帧逻辑。

`SKILL.md` 的内容组织为：

| 段落 | 必须表达的决策 |
| --- | --- |
| 输入 | 视频、带时间的转写、输出目录；来源 URL 可选；缺输入时交回调用者获取 |
| 开始前 | 核对媒体与字幕来源、分集和时间范围；读取已有进度 |
| 生成 | 按连续时间窗口阅读转写并查看对应画面，写 Markdown 并记录配图意图 |
| 选图 | 使用真实时刻提图，查看单帧，调整不清晰、过渡或不对应的配图 |
| 合并 | 去除机械重复，修复跨窗口语句和小节，保留重要步骤、例子与图文关系 |
| 导出 | 调用同源 Markdown→HTML 工具，检查图片、标记和资源完整性 |
| 完成 | 范围内输入已处理，正文可读、图文对应、导出可打开；报告来源和未解决问题 |

详细写作规则放 `references/note-style.md`；内部数据结构和恢复规则放 `references/output-contract.md`。主文件直接指明在写作前、生成结构化数据前分别读取相应参考，避免把必要规则藏在无人读取的文件中。

写作风格以 BiliNote 的教程风格为起点：按讲解推进形成小标题；允许归纳与合并无新增信息的重复；步骤保留前提、操作、结果和必要解释；代码、命令、路径、版本和参数依据真实来源保留。内容未说明的版本、菜单名、下载地址或操作结果不能靠常识补造。

无需让每个小节都有图片、表格或总结。安装教程中，适合配图的位置通常是关键选项、路径设置、软件界面变化、安装完成或验证结果；最终由实际画面决定。没有清晰证据时保留说明或标记待核查，不用图注制造不存在的视觉信息。

两个技能均允许正常发现和直接调用，保留简短的通用 YAML frontmatter。可选 `agents/openai.yaml` 只提供 Codex UI 信息，不承载核心逻辑，不把模型供应商或具体工具名写成唯一执行途径。

仓库当前 `bin/install.mjs` 已递归复制包含 `SKILL.md` 的完整目录，原则上可安装新技能，无须新增安装器。PR 要在临时 `CODEX_HOME` 中验证 `scripts/`、`runtime/`、`references/` 和 `assets/` 均被复制，且从已安装位置也能执行。测试安装不覆盖真实用户目录；正式安装只更新两个新 Skill，不使用全局 `--force` 顺带替换无关技能。两个 README 增加能力和依赖说明；其他 learning 文件保持原样。

## 7. 工具接口：拟实现契约

以下命令尚不存在，给后续实现规定可组合的接口。调用者先定位 Skill 目录，再解析相对入口；用户路径、视频路径和输出目录均为明确参数。

### 画面工具

```text
video-frames preview --video PATH --start SECONDS --end SECONDS
                     --interval 6 --grid 2x2 --output-dir PATH

video-frames capture --video PATH --plan PATH --output-dir PATH
```

`preview` 返回 `preview.json` 及图片清单，记录每个格子的原视频绝对时间。支持小数秒和超过一小时的时间；时间单位统一为秒。采样最后不足间隔的尾段也应有明确处理，窗口结尾不因拼图凑组被丢弃。

`capture` 读取配图计划中 `figures`，返回截图结果清单，关联 `figure_id`、请求时间和文件。仅在实际测得帧 PTS 时提供该字段，否则明确为未测量，不伪造帧级精度。截图失败、文件缺失、空文件或时间越界产生结构化失败结果，不能生成一个看似成功的图片链接。

### 笔记工具

```text
video-notes prepare --video PATH --transcript PATH --source-url URL
                    --work-dir PATH --window-seconds 120

video-notes assemble --draft PATH --plan PATH --captures PATH
                     --output-dir PATH

video-notes render --markdown PATH --output-dir PATH

video-notes validate --plan PATH --output-dir PATH
```

`prepare` 检查媒体、规范化字幕并建立时间窗口；支持当前案例的 SRT 和 local-whisper 的带 `segments[{start,end,text}]` JSON。其他格式在真实需要时再扩展。它能发现格式、明显时长或标识异常；音画语义匹配由智能体查看和听取素材确认。不能因总时长不同自动拉伸字幕。

`assemble` 验证配图计划和截图结果，将 Markdown 中的标记换为相对图片路径及图注，复制被实际使用的图片。`render` 只从成稿生成 HTML；样式调整不触发模型写作。渲染以 Markdown 所在目录为图片资源根，若输出到另一目录，须复制实际引用的图片并保持相对路径有效。`validate` 检查数据和文件不变量，返回报告，不宣称能自动判断解释充分度或图文语义正确性。

所有入口 stdout 返回简洁 JSON，stderr 输出进度；失败返回非零退出码和可定位原因。依赖操作保持顺序，截图和导出成功后再推进对应状态。现有文件默认复用或生成新结果，不静默覆盖来源。

## 8. 最小文件协议与长视频处理

Markdown 是正文的维护格式，避免将整份正文同时保存在 JSON 中。任务工作目录保存：

```text
work-dir/
  transcript.json          # 带稳定 segment ID 的规范化来源
  job.json                 # 输入指纹、窗口与阶段、文件位置
  note-plan.json           # 配图意图及必要来源关联
  chunks/0001.md           # 按连续窗口生成的可恢复草稿
  chunks/0002.md
  draft.md                 # 合并后的正文，含图片占位标记
  previews/                # 模型浏览素材
  captures/                # 最终截图及结果清单
```

`job.json` 和 `note-plan.json` 各有一份职责明确的状态，不重复维护阶段。`job.json` 保存媒体来源 URL、本地视频路径、分集 ID、视频/转写指纹、窗口范围及已阅读/草稿/审阅阶段；`note-plan.json` 保存配图记录。原始字幕保留，规范化只映射字段与时间、分配 ID，不改写识别内容。

配图协议示意，时刻仅为字段示例，不是本视频的实际选图：

```json
{
  "schema_version": 1,
  "figures": [
    {
      "id": "f001",
      "timestamp": 143.2,
      "caption": "由实际画面确认的说明",
      "source_segment_ids": ["seg00042"],
      "reason": "该画面能解释相邻步骤"
    }
  ]
}
```

在 `draft.md` 中用 `<!-- figure:f001 -->` 表达插图位置。ID 而非自由文本时间承担匹配，工具校验唯一性及存在性；时间链接由保存的媒体 URL 和分集生成。最终 Markdown 中不残留内部标记。图注和时间既可用于阅读，也可回溯来源。

窗口从 120 秒起步，可随语义边界和上下文容量调整。窗口负责分批读取，不直接决定最终小节边界；跨窗口句子和转写段应保留完整。给模型少量上文与术语作为只读上下文，处理记录区分实际负责的来源段与重叠上下文，合并时消除机械重复。

每窗默认约 20 个预览帧、5 张 2×2 拼图；整集约 215 个预览帧、11 个工作窗口，具体数量取决于边界取整。模型实际读完对应文字与图片后再记录完成，不能用“生成过预览文件”代替看过画面。摘要模式允许略去片头和无新增信息的重复，不要求逐字覆盖；重要内容遗漏通过全文对照发现。

每完成一个窗口保存草稿及进度。恢复时检查输入、配图配置和提示词版本；变更只使受影响阶段失效。每个任务使用独立目录。第一版顺序处理一集，不强制多智能体；具备图片查看、文件读写和命令调用能力的模型都能按同一协议执行，工具代码中不调用 LLM。

## 9. 输出与阅读样式

```text
output-dir/
  note.md
  note.html
  images/
  assets/note.css
  sources/transcript.srt   # 输入为 SRT 时保留原件
  sources/transcript.json
  sources/source.json     # 标题、原 URL、P2、媒体 ID、来源核对说明
```

HTML 从 `note.md` 同源渲染，提供目录、舒适行宽、清楚的标题层次、步骤列表、表格、代码高亮、图片放大、原视频时间跳转和打印样式。初版通过 CSS 和普通静态 HTML 完成，不建立 React 应用。语义标签和图片 alt 来自实际图注。

CSS、图片和必要脚本随包提供，基础阅读不依赖 CDN、后台服务或在线模型；移动整个输出目录后仍可阅读。原片跳转需要网络，与离线正文阅读分开。数学渲染和其他复杂插件按案例真实需求再加入。

媒体文件、安装包、预览缓存和个人运行状态均在仓库外。默认不复制完整视频到输出包。

## 10. media_operator 的最小接入

新增一条意图路由：

```text
视频笔记请求
  → 解析来源和分集，检查已有媒体与转写
  → 缺视频：现有下载 Skill
  → 缺可靠字幕：平台字幕或 local-whisper
  → video-notes（需要画面时使用 video-frames）
  → 核对成稿并返回输出路径
```

在本机配置中注册两个新 Skill，其他媒体功能继续按原路径执行。新笔记分支使用笔记自己的完成条件；现有 `dubbing.json` 和音频完成条件仅用于配音任务。

仓库不预设其他机器的绝对 Skill 路径。`video-notes` 通过宿主技能发现机制定位 `video-frames`；宿主没有该机制时，调用者提供其明确路径。找不到时报告缺少依赖，不能在笔记工具里复制一份抽帧实现或偷偷下载安装。

现有本机媒体智能体配置位于仓库外。PR 中先提供接入说明和配置片段，实施时对本机配置做最小修改并记录差异。通用技能内容不包含用户名、Codex 专属工具 API 或固定模型名。

## 11. 用 P2 跑通的实施顺序

### A. 在新工作树实现可测试的工具

建立分支后先完成画面工具、字幕规范化、截图替换、渲染和校验，使用仓库外生成的小型测试视频及字幕验证。再编写两个短 Skill、参考文件与模板，避免把一次性案例脚本作为最终实现。

### B. 获取并确认 P2 素材

1. 通过现有下载技能 inspect 带 `p=2` 的 URL，确认 `_p2` 标识。
2. 下载或复用经过确认的 P2 视频，检查实际时长和清晰度。
3. 核对现有候选 SRT；匹配才复用，不匹配则保留原文件并对 P2 本地 ASR。
4. 建立来源元信息，源 URL、分集与本地文件路径分别记录。
